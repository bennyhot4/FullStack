# MCP server: let users and admins work through AI assistants, securely

Status: active
Owner: bennyhot4
Last updated: 2026-11-22

## Goal
Add a remote **MCP (Model Context Protocol) server** to the API so a signed-in person can connect an AI
assistant (Claude, ChatGPT, Cursor, VS Code, ...) to HourOffice and work in plain language. **What the
assistant can do is limited by the person's role and by what they approved**:
- a **user** books and cancels their own bookings, sees offices and free slots, and links a booking to one of
  their clients (client names only, unless they explicitly approve full client details);
- an **admin** can also manage bookings, offices, branding and settings, and read analytics and users.

The same rules, permissions and gates as on the site apply to every call, and nothing more.

Security is the main deliverable, not an add-on. The person must be able to:
- connect an assistant only through an explicit consent screen, signed in with Google (§0 #3),
- grant the smallest set of permissions (scopes) and see what they granted,
- disconnect it at any time, with immediate effect,
- trust that every hop is encrypted and that personal data at rest is encrypted.

The owner must be able to switch the whole feature off in seconds without a code change.

This follows `docs/PLAN.md` §0:
- #2: the site and the API stay two separate deployments. The MCP server lives in the API container
  (no third deployment); the site only adds a consent page and a "Connected apps" page.
- #3: Google sign-in only. The OAuth server added here never asks for a password; it signs the person in
  with the existing Google flow and then asks for consent.
- #4: no emails or messages are sent.
- #7: every new secret (signing and encryption keys, KMS access) lives only in Secret Manager / env vars.

## Scope

### Background: what "MCP server" means here
- **Transport:** MCP *Streamable HTTP* on one endpoint, `POST /mcp` (`GET /mcp` returns 405, as the server sends
  no unsolicited messages). Run **stateless** (no `Mcp-Session-Id` state in memory) because Cloud Run scales to
  zero and may run 2 instances with no sticky sessions.
- **SDK:** the official C# SDK `ModelContextProtocol.AspNetCore` (NuGet), pinned to an exact stable version.
- **Authorization:** the MCP authorization spec (OAuth 2.1). The MCP endpoint is an OAuth *resource server*,
  and the API also hosts the OAuth *authorization server* that issues tokens for it, built on **OpenIddict**
  (open-source OAuth/OIDC server for ASP.NET Core, with a MongoDB store). Decided in Q2.

### Scopes
Scopes are what the person approves on the consent page. A tool is listed and callable only when **both** the
person's current role (reloaded from the DB on every call) **and** the granted scopes allow it.

| Scope | Who can grant it | Consent page default | Meaning |
|---|---|---|---|
| `offices:read` | everyone | checked | offices, free slots, booking rules |
| `bookings:read` | everyone | checked | own bookings |
| `bookings:write` | everyone | checked | create / cancel own bookings, link a booking to a client |
| `clients:basic` | everyone | checked | own clients' **first and last name and id only** (to pick a client for a booking) |
| `clients:full` | everyone | **unchecked**, with a warning | own clients' full details: phones, emails, notes |
| `admin:read` | admins only | unchecked | all bookings, all offices, analytics, users list |
| `admin:write` | admins only | unchecked, with a warning | edit/cancel any booking, recurring bookings, create/edit offices, branding and settings |

`admin:*` scopes are not even offered to a non-admin. If an admin is later demoted, the admin tools stop
working on the next call (role is checked from the DB, not from the token) and disappear from `tools/list`.

### Tools
Every tool calls the same service code as the matching REST endpoint.

**User tools**
| Tool | Scope | Annotations | Same rules as |
|---|---|---|---|
| `list_offices` | `offices:read` | read-only | `GET /api/offices` (available offices only) |
| `get_office_availability` `{officeId, date}` | `offices:read` | read-only | `GET /api/offices/{id}/availability` |
| `get_booking_rules` | `offices:read` | read-only | open hours, max days ahead, slot size, currency (`/api/settings/public`) |
| `list_my_bookings` `{tab, clientId?}` | `bookings:read` | read-only | `GET /api/bookings/mine` (client name included only with `clients:basic`) |
| `create_booking` `{officeId, date, startTime, endTime, notes?, clientId?}` | `bookings:write` (+ `clients:basic` for `clientId`) | write | `POST /api/bookings` (profile + terms gates, `BookingRules`, `409 slot_taken`) |
| `cancel_booking` `{bookingId}` | `bookings:write` | destructive | `POST /api/bookings/{id}/cancel` (owner only; plan 005 warning when it lands) |

**Admin tools** (role `admin` checked on every call)
| Tool | Scope | Annotations | Same rules as |
|---|---|---|---|

| `admin_create_office` / `admin_update_office` | `admin:write` | write | `POST` / `PUT /api/admin/offices` (including the available switch) |

**Stays on the site only (never via MCP):** deleting users or offices, changing a user's role or email,
inviting users, publishing a new terms version, the MCP on/off switch and revoking connections, signing the
terms and editing one's own profile. These are either irreversible, change who can do what, or need the person
to read and sign. Distribution lists are not exposed (Q4).

### New API surface (`backend/HourOffice.Api`)
| Method | Path | Purpose |
|---|---|---|
| POST | `/mcp` | MCP Streamable HTTP endpoint (Bearer token, audience = MCP resource) |
| GET | `/.well-known/oauth-protected-resource` | Protected Resource Metadata (RFC 9728): resource URL, authorization server, scopes |
| GET | `/.well-known/oauth-authorization-server` | Authorization Server Metadata (RFC 8414) |
| POST | `/oauth/register` | Dynamic Client Registration (RFC 7591), restricted (S7) |
| GET | `/oauth/authorize` | Authorization Code + PKCE; redirects to the site consent page |
| GET | `/oauth/authorize/request/{id}` | The consent page reads the pending request: client name, redirect host, verified flag, requested scopes |
| POST | `/oauth/authorize/decision` | Called by the consent page with the site token: approve (with the chosen scopes) or deny |
| POST | `/oauth/token` | `authorization_code` and `refresh_token` grants |
| POST | `/oauth/revoke` | Token revocation (RFC 7009) |
| GET | `/api/me/connected-apps` | The person's connected assistants: name, scopes, first/last use |
| DELETE | `/api/me/connected-apps/{clientId}` | Disconnect: revoke all of this person's tokens for that client |
| GET/PUT | `/api/admin/settings/mcp` | Admin: enable/disable MCP for the site; list and revoke any connection; "revoke all" |

A 401 from `/mcp` carries `WWW-Authenticate: Bearer resource_metadata=".../.well-known/oauth-protected-resource"`
so clients discover the authorization server on their own.

## Security requirements
Each item is mandatory for go-live and maps to a Validation item.

**S1. Authorization (OAuth 2.1 per the MCP spec)**
- Authorization Code flow only, **PKCE `S256` mandatory** for every client (`plain` rejected); no implicit, password
  or client-credentials grant.
- **Audience binding (RFC 8707 resource indicators):** tokens are issued for the resource `https://<api>/mcp` and
  `/mcp` rejects any other audience. The site's JWTs are **not** accepted at `/mcp`, and MCP tokens are **not**
  accepted at `/api/*` (separate scheme, issuer and keys).
- **No token passthrough:** the MCP server never forwards the token anywhere; tools call in-process services.
- Access tokens live **10 minutes**. Refresh tokens are **rotated on every use** with reuse detection (a reused
  refresh token revokes the whole chain for that person + client). Refresh lifetime: 30 days, but **7 days when the
  grant contains `admin:write` or `clients:full`**.
- Granting `admin:write` or `clients:full` requires a Google sign-in **within the last 10 minutes** (the consent page
  asks Google again if the site session is older).
- Redirect URIs: exact string match, `https` only, except loopback (`http://127.0.0.1:<port>` / `http://localhost`)
  for desktop clients. No wildcards, no fragments.
- `state` required; authorization codes are single-use and live 60 seconds.

**S2. The same authorization rules as the site, by role**
- Every tool call reloads the person from the DB (like `RequireUser()` / `RequireAdmin()`). A deleted, not-`active`
  or demoted person fails immediately even with a valid token.
- A tool runs only if the role allows it **and** the scope was granted. Missing scope → `403 insufficient_scope`
  with the needed scope in `WWW-Authenticate`; wrong role → `admin_required`, like the REST API.
- Profile and terms gates apply exactly as on the site (`terms_required`, `profile_required`, with a message to
  open the site).
- Ownership is checked inside the Mongo query (someone else's booking or client id → `not_found`, never
  "forbidden", so ids cannot be probed). A client id in `create_booking` / `set_booking_client` must be the caller's
  own client.
- `clients:basic` without `clients:full` is enforced **on the server** by a separate DTO (`ClientNameDto`) that has no
  phone, email or notes fields; the full DTO is built only when `clients:full` was granted.
- Business logic moves out of the endpoint files into services (`Services/BookingService.cs`, `OfficeService.cs`,
  `ClientService.cs`, `SettingsService.cs`, `AnalyticsService.cs`) called by **both** the REST endpoints and the
  tools, so the two can never drift apart.

**S3. Consent and the person's control**
- Consent is per person + client + scope set; asking for a scope not yet granted means a new consent screen.
  The person may uncheck any requested scope; the token gets only what was checked.
- The consent page is served with `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`
  (via `public/_headers`) against clickjacking. The decision call needs the site's Bearer token (which a cross-site
  form cannot send) plus the request id it was given (CSRF).
- Disconnect revokes every token of that person + client. Tokens are validated against `oauthTokens` on each call
  (Q6), so revocation takes effect on the very next call.

**S4. Prompt injection and tool poisoning**
- Tool names and descriptions are static strings in code, never built from DB data. The tool list depends only on
  role and granted scopes, never on data (no "rug pull").
- Text written by people (office names/descriptions, booking notes, client names, branding text) is returned only in
  fields of the **structured result** (`structuredContent` with an `outputSchema`), trimmed to its max length,
  control characters removed; tool descriptions say these fields are user content, not instructions.
- Tools return only what the person can already see on the site. Availability shows busy/free slots, never other
  bookers' names. Admin tools return the same fields the admin pages show.

**S5. Human confirmation for actions with effects**
- Write tools are annotated `readOnlyHint: false`, and cancel/delete tools `destructiveHint: true`, so clients show
  their approval prompt.
- If the client supports **elicitation**, the server asks the person to confirm the exact change before writing
  (booking details and price; for recurring bookings the number of dates; for branding the old and new values).
- Without elicitation, every write result states clearly what was done and how to undo it.
- Per-person limits via MCP, beyond the normal rules: 10 bookings created and 10 cancelled per hour (user tools);
  30 admin writes per hour; recurring bookings via MCP limited to 90 days per call (the site keeps 366).

**S6. Input validation**
- Every tool has a strict JSON Schema (`additionalProperties: false`): ObjectId format for ids, `yyyy-MM-dd` dates,
  `HH:mm` times, `notes` ≤ 500 characters, colors `#RRGGBB`. Invalid input → tool error with an `invalid_*` code;
  server rules (`BookingRules`, branding validation) still run after the schema.
- `admin_upload_image`: decoded size ≤ 5 MB, `mimeType` in jpg/png/webp **and** the file's magic bytes match it,
  stored through the existing `IFileStorage` under a server-generated name. Upload is from data sent in the call
  only; **no "image from URL"** (prevents SSRF).
- Request body limit on `/mcp`: 8 MB (for the upload tool); every other tool rejects arguments > 16 KB.

**S7. Abuse and availability**
- Rate limits (`AddRateLimiter`): `/oauth/*` 30/min per IP (like `"auth"`), `/oauth/register` 10/hour per IP,
  `/mcp` 60 calls/min per person + client.
- Dynamic registration: public clients only (`token_endpoint_auth_method: none`), name ≤ 100 chars, ≤ 5 redirect
  URIs; a client that never completed consent is deleted after 24 hours; the consent page marks every dynamically
  registered client "not verified". Claude and ChatGPT are pre-registered by their published redirect URIs and shown
  as verified (Q7).
- Request timeout 30 s per tool call.
- `Origin` header check on `/mcp`: a browser origin not in `Mcp:AllowedOrigins` is rejected (DNS-rebinding defence
  from the MCP transport spec). No CORS on `/mcp` and `/oauth/token`.
- Kill switch: `Mcp__Enabled=false` (env) or the admin switch → `/mcp` and `/oauth/*` return 503 immediately.

**S8. Logging and audit**
- Every tool call writes one `mcpAuditLog` row (no arguments, no tokens, IP hashed).
- Logs never contain tokens, authorization codes, PKCE verifiers, notes, phones, emails or image data (see the
  `error-handling` skill: redaction). OpenIddict token logging stays off in Production.
- Failed auth bursts (≥ 20 401s per IP per minute) and every `admin:write` call are logged at warning/info level so
  Cloud Logging can alert.

## Encryption ("end to end")
**What is and is not possible.** In MCP the AI assistant must read the data to answer, so the assistant's provider
(e.g. Anthropic, OpenAI) necessarily sees the tool results in plain text. Encryption that only the person can read
cannot exist for this feature. This plan guarantees that the data is encrypted **on every hop and at rest**,
readable only by the API process and the person's own assistant session, and that the provider gets the minimum
(S4, `clients:basic` by default). The consent page and the privacy policy say this plainly (Q5).

**E1. In transit (every hop)**
| Hop | Protection |
|---|---|
| Assistant → `/mcp`, `/oauth/*` | HTTPS only, TLS 1.2+ (Google front end on `*.run.app`); HSTS `max-age=31536000; includeSubDomains`; HTTP is not served |
| Browser → site (`/McpConsent`, `/ConnectedApps`) | HTTPS on Cloudflare Pages, HSTS |
| API → MongoDB Atlas | TLS required (`tls=true`, Atlas enforces it) |
| API → R2, Google token check, Cloud KMS | HTTPS |

**E2. Tokens**
- Access tokens are **signed and encrypted** (JWE, OpenIddict's default), so their content (person id, scopes) is
  not readable by the client or anyone who intercepts them.
- Refresh tokens and authorization codes are stored only as hashes (as `TokenService` already does for the site).
- Signing key and encryption key are separate, held in Secret Manager, never in the image; rotated every 6 months
  with an overlap period (old keys still validate, new keys sign).

**E3. At rest (Phase C, part of this plan per Q8)**
- **Atlas default:** the storage volume is encrypted (AES-256) by the provider. In place today; protects against
  stolen disks only, not against someone who reaches the database.
- **Field-level encryption of personal data** with MongoDB **Client-Side Field Level Encryption, explicit mode**
  (works on Atlas M0, unlike automatic encryption), done by the API before writing:
  - Encrypted fields: `users.phone`, `clients.phones`, `clients.emails`, `clients.notes`, `bookings.notes`.
  - Algorithm `AEAD_AES_256_CBC_HMAC_SHA_512-Random`; `-Deterministic` only where an equality search is needed
    (step 13 checks every query on these fields first; today none filter by them). Names stay unencrypted because
    the site and `clients:basic` search and sort by them.
  - Data keys live in the `encryptionKeys` key vault collection, wrapped by a **customer master key in Google Cloud
    KMS** (key ring `houroffice`, key `mongo-cmk`, `europe-west1`); the Cloud Run runtime account gets only
    `roles/cloudkms.cryptoKeyEncrypterDecrypter` on that one key. Cost: about $0.06/month plus a few cents of calls.
  - Result: a leaked database dump or a stolen Atlas password does not reveal phones, emails or notes.
  - Migration: a resumable startup pass (marker `fields_encrypted` in `siteSettings`, like `admin_clients_filled`)
    encrypts existing documents; readers accept both plain and encrypted values until the marker is set.
  - Released **after** MCP v1 is live (Rollout step 5) and behind its own option `FieldEncryption:Mode`
    (`off` / `encrypt` / `decrypt`), so it has its own gate and rollback.

- Plan 004 (CI/CD, staging) is not done, so production deploys are still the manual runbook in
  `.doc/operations.md`; there is no staging environment.

  Streamable HTTP with OAuth discovery and dynamic client registration. Clients that need the newer "Client ID
  Metadata Documents" are handled in step 4 if needed.

  new paths end in `z` (Google reserves those on `*.run.app`).
- Clients' phones and emails reaching an AI provider with `clients:full` is the person's own explicit choice (opt-in,
  unchecked by default, warning shown) and is covered by the privacy policy update (Q4, Q5).

**Security review fixes (2026-11-22, security-reviewer agent)**
- M1: "signed in within 10 minutes" is per session. The site access token carries `auth_time`; `refreshTokens.authTime`
  copies it unchanged to each rotated token. Before, `users.lastLoginAt` let an old or stolen session approve
  sensitive scopes right after the owner signed in elsewhere.
- M2: `admin:write` / `clients:full` end 7 days after the consent. A private claim `ho_sensitive_until` (code and refresh
  token only) sets each refresh token's lifetime to the time left, so refreshing no longer slides the 7 days.
- M3: admin tools return users' phones and booking notes only with `clients:full` too; `admin:read` alone shows them
  empty. The consent label for `admin:read` says so.
- L1: `McpText.Clean` works on Unicode scalars: drops Control/Format (except ZWJ/ZWNJ), separators, private use,
  variation selectors, tag characters and lone surrogates, and never cuts a character in two.
- L2: per-hour write limits reserve their audit row (`outcome: "reserved"`) before counting, so parallel calls cannot
  pass together; the filter turns the reservation into the final row, and a failed or declined call frees it.
- L3: `/oauth/authorize` requires `state` (≤ 500 characters).
- Not changed: L4 (forwarded headers trusted from any proxy; fine behind Cloud Run's front end, which is the only way
  in), writes without confirmation on clients without MRTR, and `imageUrl` accepting any URL (noted as follow-ups).

## Risks
- **OAuth is easy to get subtly wrong.** Mitigated by OpenIddict instead of hand-written protocol code, the
  negative tests above and a dedicated security review.
- **Admin power through an assistant.** A confused or injected assistant could change bookings, offices or
  branding. Mitigated by opt-in `admin:write` with a warning and fresh sign-in, a 7-day refresh, approval prompts
  and elicitation, per-hour limits, the audit log, irreversible actions kept site-only, and instant disconnect.
- **The AI provider sees tool results** (inherent to MCP), including other people's data for admins and for
  `clients:full`. Mitigated by data minimization (S4), `clients:basic` by default, and clear wording on the consent
  page and in the privacy policy.
- **Launching to everyone on day one** with no staging: a bug reaches all users who connect. Mitigated by the owner's
  production check before the announcement and the kill switch (seconds).
- **MCP spec and client support move fast.** Pin the SDK, test with two real clients, keep the kill switch.
- **Cold starts** on Cloud Run make the first call after idle take a few seconds; min-instances stays 0 to keep cost ~$0.
- **Phase C:** losing the KMS key means losing the encrypted fields (disable-not-destroy policy, 30-day scheduled
  destruction, Atlas backup before enabling); rollback after the migration needs the decrypt pass.

## Rollout Order
Production deployment (manual runbook until plan 004 automates it):
1. **Secrets:** create `mcp-signing-key` and `mcp-encryption-key` in Secret Manager (generated locally, never printed
   in chat or logs); grant the runtime account `secretAccessor` on them only.
2. **API + site deploy, dark:** new Cloud Run revision from the merged commit with `Mcp__Enabled=false`,
   `Mcp__Issuer=https://<run.app URL>`, `Mcp__Resource=https://<run.app URL>/mcp`, `--set-secrets` for the two keys;
   Cloud Run settings unchanged (max 2 instances, scale to zero). Smoke: `GET /api/settings/public` 200,
   `POST /mcp` 503. Upload the new `dist/` (plan 010 runbook); the Google OAuth client needs no change (same origin).
3. **Switch on, owner check (same day):** set `Mcp__Enabled=true` (new revision; the admin switch is on by default). The owner connects Claude and ChatGPT, runs every
   user tool and every admin tool, disconnects, and checks the audit log and Cloud Logging for errors and leaked
   values. Any problem → switch off and fix.
4. **Announce to everyone** (README guide, site banner). Watch for 7 days: Cloud Run errors, 401/429 rates,
   `admin:write` log lines, budget alert.
5. **Phase C release** (after step 4 is quiet for a week): create the KMS key ring and key, grant the runtime account
   the single encrypt/decrypt role, the owner takes a `mongodump` of Atlas (stored offline), deploy with
   `FieldEncryption__Mode=encrypt`, wait for the migration marker, verify with `mongosh`.

## Rollback
- **Fastest (seconds):** turn the admin switch off, or set `Mcp__Enabled=false` (new revision, no rebuild). `/mcp` and
  `/oauth/*` stop answering; the site and REST API are unaffected.
- **Revoke every connection:** admin "revoke all"; people reconnect later through consent.
- **Code rollback:** route Cloud Run traffic to the previous revision. The OpenIddict collections are additive and
  ignored by old code (the convention pack ignores unknown elements). Site: Cloudflare Pages one-click rollback.
- **Leaked signing/encryption key:** new keys as new secret versions, redeploy; all tokens become invalid and people
  reconnect.
- **Phase C:** deploy with `FieldEncryption__Mode=decrypt`, wait until the pass reports every document plain, then
  `Mode=off` or the previous revision (an older revision cannot read encrypted fields, so never roll back past the
  decrypt step). If the KMS key itself is lost, restore from the `mongodump` taken in Rollout step 5.
